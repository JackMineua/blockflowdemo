# blockflowdemo
Частина 0:
1. User Scenarios (Сценарії користувача)
Запуск обробки: Користувач завершує введення даних (вага, ціль) і на останньому екрані обирає метод обробки: WebSocket або HTTP. Це створює завдання (job) на сервері через POST /jobs.
Отримання результату: Користувач спостерігає за прогресом (реальний час для WS або циклічне опитування для HTTP). Після завершення (статус done) з'являється фінальний результат та кнопка Reset для повернення на перший крок.

2. Job Processing та оновлення статусів
Як працює Processing: Сервер виконує pipeline із декількох послідовних кроків (функцій) з емуляцією затримки (setTimeout).
Оновлення статусу:
Джерело даних: БД SQLite є єдиним джерелом правди.
WebSocket: Сервер активно надсилає статус та % прогресу клієнту при кожній зміні в БД.
HTTP (Polling): Клієнт самостійно робить GET /jobs/:id запити, щоб прочитати актуальний стан з БД.


Частина 2: Архітектура
Прийняті рішення для реалізації бекенду:

Модульність: Код розділений на три частини: API (контролери), Logic (керування завданнями) та Pipeline (виконання кроків).

Стани завдання: Реалізовано перехід між станами queued -> processing -> done/failed.

Persistence (БД): Використано SQLite для мінімалістичної інтеграції та збереження даних без складних ORM.

Гнучкість Pipeline: Обробка побудована так, що нові кроки можна додавати як окремі модулі/функції без зміни логіки сервера.
